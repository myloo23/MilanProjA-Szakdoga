3. tananyag · ~12 perc · a dolgozat 4.6 és 5.3 alfejezete

Helm

A chart, a values, a release és a revízió, és hogyan futtatja a pipeline a Helmet a gépen.

Röviden
  • A chart sablonok + alapértékek. Telepítéskor egyetlen értéket cserélsz: --set image.tag=<sha>.
  • Minden telepítés és minden rollback egy új, sorszámozott revízió.
  • A kézi oldal és a pipeline ugyanazzal a Helm-verzióval (3.22.0) ugyanazt a chartot telepíti.

1. Mit ad a Helm a sima kubectl apply-hoz képest

Probléma kubectl-lelHelm-megoldás
A változó értékek (tag, replikaszám) be vannak égetve a YAML-be.Sablon + values: {{ .Values.image.tag }}, telepítéskor adod meg.
Sok fájl, semmi nem tartja össze őket.Release: az egész app egy néven (projecta) települ és frissül.
Nincs „vissza az előzőre”.Revíziók: bármelyikre vissza lehet állni egy paranccsal.

Helm váltja az Ansible-t a telepítésben

Miért: a kézi oldal is Helmmel telepít; egy release, egy kapcsoló mozgatja az egész alkalmazást, és a rollback egy parancs.

Nélküle: a pipeline deploy jobja a mérés előtt még Ansible-lel egy Docker-konténert telepített, nem a fürtre. A két oldal két különböző célpontot mért volna, és ez a táblázatból nem látszott volna.

Hol: ADR-0009, napló 2.7

2. A chart

A sablonok: backend.yaml, frontend.yaml, postgres.yaml, db-schema.yaml, ingress.yaml. A values.yaml lényege:

image:
  registry: localhost:5001   # a gépen futó registry
  tag: dev                   # EZT cseréli minden telepítés
backend:  { image: { repository: projecta-flask },    replicaCount: 2 }
frontend: { image: { repository: projecta-frontend }, replicaCount: 2 }

Egy közös tag mindkét saját képre

Miért: a backend és a frontend ugyanabból a commitból épül, tehát egy verziószám írja le a kiadást, és egy --set váltja.

A buktató, ami kiderült: a pipeline eleinte csak a backend képet építette. A közös tag miatt a frontend pod olyan képet keresett volna, ami nincs: ImagePullBackOff. A mérés előtt javítva.

Hol: chart/values.yaml, napló 2.7

3. Renderelés: sablon + értékek = YAML

A Helm összefésüli a sablonokat az értékekkel, és a kész YAML-t küldi az API szervernek. A sablon (egyszerűsítve) {{ .Values.image.registry }}/{{ .Values.backend.image.repository }}:{{ .Values.image.tag }} sorából így lesz localhost:5001/projecta-flask:e4da1d9. A helm template chart ezt telepítés nélkül megmutatja; sablonhibánál ezzel kezdj.

Megváltoztatja a --set image.tag=x a values.yaml-t?

Nem. Csak erre a telepítésre írja felül, de a Helm eltárolja a revízióval: a helm get values projecta megmutatja. A pipeline pont ebből olvassa ki, mi fut most.

4. Release és revízió

A release a chart egy telepített példánya (projecta). Minden helm upgrade és helm rollback új revíziót hoz létre; a Helm mindegyik teljes tartalmát eltárolja a fürtben, ezért tud bármelyikre visszaállni.

Három revízió után rollback. Hány revízió lesz?

Négy. A rollback nem töröl és nem „ugrik vissza”: új revíziót csinál a régi tartalmával. Az előzmény így teljes marad.

Miért upgrade --install, és nem külön install és upgrade?

Mert mindig ugyanaz a parancs: ha nincs release, telepít, ha van, frissít. Ez idempotens, a pipeline-nak nem kell tudnia, először fut-e.

5. Hogyan futtatja a pipeline a Helmet

A deploy job egy konténerben fut a gépen. A k3s API a gép 127.0.0.1:6443-as címén figyel, és a tanúsítványa csak a 127.0.0.1-et, a localhost-ot és a publikus IP-t nevezi meg. A job konténeréből ez a cím nem érhető el, a Docker-híd címe (172.x) pedig nincs a tanúsítványon.

Helm a gép hálózatán: scripts/helm-on-host.sh

Mit csinál: a gép Docker-socketjén át indít egy alpine/helm:3.22.0 konténert --network host-tal. Ott a 127.0.0.1:6443 az API szerver, pont mint a kézi operátornak. A chartot git archive-val másolja be a tesztelt commitból.

Az alternatívával: a TLS-ellenőrzés kikapcsolása biztonsági hiba lenne; a tanúsítvány átírása a k3s telepítését módosítaná egy CI-részlet kedvéért.

Miért 3.22.0: a kézi oldal is ezt használta (E1). Ha a két sorozat más Helm-verzióval telepítene, az egy második változó lenne az ágnév mellett.

Hol: scripts/helm-on-host.sh fejléce

6. Két ütközés, amibe belefutottál

„invalid ownership metadata”: egy kézzel (kubectl apply) létrehozott erőforrásra a Helm nem teszi rá a kezét, mert nem tudja, kié. Megoldás: állapotmentest törölsz, és a Helm újra létrehozza (backend); adatot tartalmazót jelölésekkel veszel át (Postgres, különben a PVC-vel az adat is elveszett volna).

„conflict … kubectl-client-side-apply”: mezőszintű ütközés. Egyes mezőket a kubectl állított be, a Helm nem írja felül őket csendben. Egyszer kell a --force-conflicts.

Miért ne kerüljön a --force-conflicts a pipeline-ba?

Mert az ütközés hasznos jelzés: ha valaki kézzel átír valamit a fürtben, a következő telepítés szól, nem írja felül csendben. Egy olyan dolgozatban, ami az emberi beavatkozásokat méri, ezekről tudni akarsz.

Puska

helm template chart                                    # mit küldene be
helm upgrade --install projecta ./chart --set image.tag=<sha>
helm history projecta                                  # revíziók
helm rollback projecta                                 # az előző revízióra
helm get values projecta                               # milyen tag fut most
